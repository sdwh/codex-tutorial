WHEN TO PLAN

任務大小決定工作方式

直接執行

單一明確檔案、行為簡單、容易回復，例如標籤文字或一個小 bug。

先 Plan

跨多檔、資料模型或 API 變動、尚未釐清依賴、可能改變使用者流程。

先調查再 Plan

未知 repo、legacy 系統、沒有可靠測試、需求衝突或安全 / 資料風險較高。

計畫不是文件儀式。它應該讓風險、分工、驗收和先後順序在寫程式之前變得可見。
CASE / FILTERED CSV EXPORT

案例：匯出篩選後的會員名單

客服需要依目前搜尋詞、狀態和日期區間匯出名單。大量資料不能只匯出目前頁面；姓名可能含逗號、CSV 要支援 Excel；角色權限只允許主管匯出。

這是跨 UI、資料查詢、授權和測試的功能，值得先規劃。

Plan 應答的問題

  1. 目前篩選狀態存在哪裡？UI 和 API 的篩選是否一致？
  2. 大量資料由前端或伺服器產生檔案？現有匯出模式是什麼？
  3. 授權在哪一層做？一般使用者應看到什麼結果？
  4. 欄位順序、文字編碼、公式注入及引號跳脫的規則是什麼？
  5. 每個階段如何驗收？哪些現有行為不能改變？
PLAN REVIEW

學會審閱計畫，不只按 Plan

範圍明確

計畫列出要碰的元件與不改的區域。

依賴正確

先確認資料流與授權，再做 UI 入口。

逐步可驗收

每個 milestone 都有可觀察的完成狀態。

風險有處理

大型匯出量、權限、檔案編碼、資料暴露有對策。

看到計畫缺漏怎麼回覆：指出「哪一步不完整、為什麼重要、如何驗收」，不要只說「再想詳細一點」。
STEER / QUEUE

工作中如何補充新資訊

當 Codex 目前方向需要改變，立即補充讓它調整本輪。

先停一下：匯出必須由後端套用角色授權，前端隱藏按鈕不能當作安全控制。請更新計畫，指出需要改的授權路徑和測試；不要繼續目前前端直出 CSV 的做法。

當目前工作方向沒問題，只是你有下一個獨立要求，可排在本輪完成後。

本次匯出功能完成並驗證後，請再更新說明文件，列出客服可以使用的欄位與權限條件。

桌面版/CLI 的 follow-up 互動依設定與版本不同；Help Center 說明 CLI 可用 Enter steer、Tab queue，桌面版可設定預設 Follow-up behavior。

LAB / 40 MIN

把案例拆成可審查里程碑

請 Codex 先調查 repo，再為 CSV 匯出建立 3–5 個里程碑。每步要求輸出：要變更的模組、依賴、成功條件、相關測試、需你決定的問題。

審查完計畫後，要求先完成第一個里程碑並回報，再決定後續實作；若你選擇一次完成，也要保留每階段驗收證據。
