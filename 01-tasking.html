CONCEPT 1 / HOW CODEX WORKS

把 Codex 當成可檢查的工作夥伴

Codex 不只是補全一行程式碼。它能在專案中讀檔、搜尋、編輯、執行本機工具，並根據結果繼續工作。因此你的任務描述要同時處理「想達成什麼」和「在哪些邊界內達成」。

你提供方向

目標、背景、限制、優先順序與完成條件。

Codex 探索並行動

理解 repo、提出計畫、查看工具結果、修改檔案。

你負責把關

校準方向、檢查操作和 diff、決定驗收。

核心觀念：一次對話是一段有狀態的工作流程。中途發現新資訊，及早補充，比最後整段重做有效。
CONCEPT 2 / TASK BRIEF

任務工作單的六個欄位

目標 Goal

描述交付結果，避免只寫「改善一下」。

背景 Context

目前行為、重現步驟、使用者、檔案或錯誤訊息。

範圍 Scope

哪些頁面、模組或資料包含在本次工作。

限制 Constraints

不可改 API、不能加套件、要支援哪些尺寸。

驗收 Acceptance

可觀察、可判斷的完成條件；避免「看起來不錯」。

驗證 Validation

要跑哪些測試、命令或畫面流程；哪些不能執行。

Context（上下文）不是越多越好。只提供會改變判斷的資訊；無關資料會稀釋焦點。
SCENARIO / CASE STUDY

案例：會員列表新增搜尋

背景

產品回報：「會員頁面不好用，幫忙加個搜尋。」目前列表有姓名、Email、加入日期。尚不清楚大小寫、空值、搜尋欄位、手機版和測試要求。

模糊指示的風險：Codex 可能只比對姓名、改錯列表、裝新套件，或漏掉空值和無結果狀態。

補成可驗收條件

  1. 搜尋姓名和電子郵件；不搜尋其他欄位。
  2. 忽略前後空格及大小寫；空查詢顯示全部。
  3. 顯示結果數；無結果時顯示明確空狀態。
  4. 不新增依賴、不改 API；沿用現有 UI 元件。
  5. 手機與桌面可用；既有排序和分頁保持。
  6. 新增搜尋邏輯測試，執行相關測試與 lint，回報實際結果。
PRACTICE / PROMPT BUILDER

練習：寫出任務工作單

可用範例值，也可以替換成你手邊真實但範圍小的需求。

先想想最容易被漏掉的條件，再產生工作單。
GUIDED PRACTICE / 35 MIN

在自己的 repo 跑一次

  1. 確認 Codex 開啟的是練習 repo、正確分支和工作目錄。
  2. 貼工作單，先請 Codex 找列表入口、資料欄位和測試位置，暫時不要改。
  3. 核對它找到的檔案是否符合 repo 結構；不符就補路徑或重新界定範圍。
  4. 若牽涉多個元件，啟用 Plan，要求列步驟、風險和驗收方式。
  5. 同意計畫後實作；發現分頁不可改，立即 steer 告訴它。
  6. 看 diff，逐條對照搜尋欄位、空值、手機版和測試條件。

留下證據：記錄關鍵檔案、補充的上下文、採納的驗收條件和實際驗證結果。

TRANSFER / 15 MIN

變體挑戰：把「登入怪怪的」變成工作單

寫出至少一個重現步驟、一項限制、兩個可觀察完成條件和一項驗證方式。試著讓一位沒參與討論的人也能執行。

理解題：「完成後看起來正常」算是好的驗收條件嗎？
