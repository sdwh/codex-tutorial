CONCEPT

把重複檢查掛在正確事件上

你已經會在任務中要求測試；現在要讓某些提醒在固定時機出現。Hook 是代理生命週期的事件處理器：收到結構化輸入，執行你提供的程式，再回傳該事件支援的結果。它適合記錄執行摘要、補入短脈絡、檢查特定工具參數。先定義「何時、檢查什麼、失敗如何處理」，不要一開始就記錄整段聊天。

本課以本機 Codex CLI 為操作環境，文件查核日期為 2026-10-10。先執行 codex --version 與 codex --help，記下版本；如果 /hooks 不存在或設定被判定無效，先核對你安裝的版本，而非假設所有 ChatGPT 網頁、Cloud、IDE 都支援相同事件。離線主實作不需帳號、不呼叫模型。官方 Hooks 文件

練習素材：pre_tool.py、allow.json、block.json。下載後在新練習資料夾執行，勿直接改動正式專案設定。

MAP

事件選型：前置、後置與停止

PreToolUse 在支援的本機工具呼叫前處理參數；PostToolUse 在執行後取得結果，適合檢視變更。SessionStart 可加入專案短摘要；UserPromptSubmit 可以檢查送出的提示；PreCompact／PostCompact 對應壓縮前後；SubagentStart／SubagentStop 對應子代理。Stop 是回合停止，SessionEnd 才是主執行緒結束，兩者用途不同。

工具事件 matcher 可比對 Bash、apply_patch 或 MCP 工具名稱；不要直接拿終端機命令字串當 matcher。Stop 與 UserPromptSubmit 的 matcher 目前會被忽略。Stop 回傳 decision:block 是要求代理繼續工作，不是拒絕整個回合；必須檢查 stop_hook_active 等欄位，避免反覆延長。先選單一 PreToolUse 實驗，完成後再增加事件。

CONFIG

建立可審查的專案設定

建議在練習用 Git 專案放 .codex/hooks.json；同一設定層也可寫 config.toml 的 inline hooks，但只選一種以免重複載入。使用者、專案與插件來源可能同時執行；高優先層不會自動替換其他來源。以下配置只攔截教材標記，請把路徑換成你複製範例的實際絕對路徑，空白路徑保留引號。

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "^Bash$",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"/absolute/path/hook-lab/pre_tool.py\"",
            "timeout": 5,
            "statusMessage": "Checking teaching marker"
          }
        ]
      }
    ]
  }
}

啟動 CLI 後開 /hooks，閱讀來源、命令與 timeout，再信任確切定義。專案層必須受信任；新增或變更定義需要重新審查。不要為了讓範例成功就跳過所有信任檢查。命令會在 session cwd 下執行，絕對路徑可讓你從子目錄啟動時仍找到腳本。設定與信任流程

LAB

離線實作：先測 JSON 合約，再接事件

下載網站提供的 examples/13/pre_tool.py、allow.json 與 block.json，或從專案複製到一個新資料夾。程式只解析 stdin，檢查 tool_input.command 是否含 HOOK_LAB_BLOCK，不會執行這段 command。這是可重現的教學標記，不是惡意命令偵測器。

python3 pre_tool.py < allow.json
python3 pre_tool.py < block.json

allow 的預期 stdout 是 {}；block 是含 hookSpecificOutput、hookEventName:PreToolUse、permissionDecision:deny 的 JSON。兩次正常回傳都可 exit 0；阻擋決定由事件輸出表達。改造 block fixture，使 command 改成 HOOK_LAB_ALLOW，再確認回到 {}。記錄輸入、stdout、stderr 與 exit code 四項證據，避免只看畫面上的一句成功。

"""Offline teaching guardrail; never executes tool input."""
import json
import sys

try:
    event = json.load(sys.stdin)
except (ValueError, TypeError):
    print("Invalid hook JSON", file=sys.stderr)
    sys.exit(1)

if not isinstance(event, dict):
    print("Hook input must be a JSON object", file=sys.stderr)
    sys.exit(1)

tool_input = event.get("tool_input", {})
command = tool_input.get("command", "") if isinstance(tool_input, dict) else ""
if not isinstance(command, str):
    command = ""
if event.get("hook_event_name") == "PreToolUse" and "HOOK_LAB_BLOCK" in command:
    print(json.dumps({"hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "Teaching marker blocked; choose HOOK_LAB_ALLOW."
    }}))
else:
    print("{}")
CONTRACT

stdout、stderr 與退出碼不能互換

每個 command hook 收到一個 JSON 物件，常見欄位包括 hook_event_name、session_id、cwd，工具事件另有 tool_name、tool_input。stdout 是與 Codex 溝通的通道；本課固定輸出有效 JSON，除錯文字送 stderr。不同事件的純文字、JSON 與退出碼解讀不同，不能用同一個回傳格式套所有事件。

對本課的 PreToolUse，JSON deny 或 exit 2 加 stderr 原因可阻擋受支援呼叫；純文字 stdout 會被忽略。一般 exit 1、無效 JSON、逾時不等於成功建立阻擋，請用錯誤 fixture 觀察其診斷並核對事件文件。不要用不受支援的 continue:false 取代 deny。腳本讀到未知欄位時應容忍，缺必要型別則回報錯誤；不依賴 transcript 的內部格式。

GUIDED

接回 Codex：用無副作用命令驗證

完成離線測試後才啟動已登入的 CLI，在受信任練習專案加入配置與腳本。請 Codex 分別執行 echo HOOK_LAB_ALLOW 與 echo HOOK_LAB_BLOCK；前者應顯示標記，後者應看到 hook 拒絕原因。這一步會使用帳號額度，請在自己的環境選擇執行。若代理改寫命令避開標記，要求保留原樣，以驗證事件而非模型自行決策。

LIMIT

Hook 是檢查層，權限仍由環境控制

不要把字串比對腳本稱為安全隔離。Hosted tools 例如 WebSearch 不走相同的本機工具 hook 路徑；某些工具可能例外，write_stdin 是已核準命令的後續輸入／輪詢，不會再次跑前置檢查。真正的讀寫、網路與密鑰邊界仍要由 sandbox、審批、帳號權限與作業系統控制。

多個匹配命令 hooks 可以同時啟動，不要依賴 A 先完成才啟動 B。共用記錄檔需要原子寫入或獨立檔案。後置事件無法撤回已發生的寫入；async hook 適合記錄，不適合阻擋。本課不輸出密鑰或完整提示，不把 fixture 外部文字當代理指示。MCP tool hooks 要已有連線；伺服器不存在與工具錯誤不會自動阻擋操作。

REVIEW

失敗變體與完成標準

用文字 not-json 當 stdin，程式應 stderr 報 Invalid hook JSON 並 exit 1；這驗證腳本的輸入錯誤處理，不能推論 Codex 已拒絕工具。把配置路徑改錯，從 /hooks 與執行事件診斷原因；再恢復正確路徑。若 hook 未執行，依序檢查 CLI 版本、專案信任、定義信任、event／matcher、實際 tool_name 與 cwd。

延伸挑戰是加入 PostToolUse 的短摘要記錄，只存事件名稱與時間，不存命令或提示原文。先寫兩個併發測試輸入，確認資料不互相覆蓋；再設定短 timeout。交付時附版本、配置、兩個正常 fixture 的結果、一個失敗結果與限制說明。能解釋「哪些事件沒有覆蓋」比顯示一個 hook 成功更有價值。

把這個練習想像成網站的測試前置檢查：有時你希望每次套用修補前都先提醒代理「產生的頁面要由來源資料重建」。提醒本身不應寫入另一份檔案或啟動新的代理任務，否則容易形成迴圈。先畫出事件與副作用：前置只讀參數、後置只寫短記錄、停止只做有限次驗收，每條線都標明何時結束。

測試紀錄可用四欄表保存：案例名稱、輸入摘要、預期結果、實際結果。至少加入無 tool_input、tool_input 是字串、command 是空字串的變體，確認程式不會把缺資料當成需要執行的命令。若未來改為要求某欄必填，請把對應案例改成明確錯誤，並說明錯誤只是程式診斷，阻擋是否成立仍由事件合約決定。

協作時把配置與腳本一起放入版本控制，審查差異時同時閱讀二者。命令路徑沒變不代表腳本內容可信；腳本依賴下載更新也可能改變行為。記下啟用的 hooks 清單、目的與維護人，每次升級 CLI 重跑 fixtures，再做一次本機事件測試。練習結束後可在 /hooks 停用這個教學 hook，避免 HOOK_LAB_BLOCK 標記影響其他工作。

若想把例子改成格式檢查，先挑一個固定本地檔案，使用純讀取的驗證程式，不從 tool_input 組合 shell 命令。驗證完成後只回報短原因與檔案位置；不要在 hook 內自行修正檔案。這樣你可以明確分辨是代理寫入、驗證失敗，還是後续修補造成的結果。
